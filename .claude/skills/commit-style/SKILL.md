# 커밋 메시지 · PR 작성 규칙

레포에 이미 쌓인 커밋이 기준이다. 새 형식을 만들지 말고 아래를 따른다.

## 절대 넣지 않는 것

- `Co-Authored-By:` 트레일러
- `🤖 Generated with ...` 푸터
- 도구 이름·모델 이름·"AI가 작성" 류의 흔적

작성 주체는 사람이다. 흔적을 남기지 않는다.

## 제목

```
type(scope): 무엇을 했는지 한 줄
```

- `type`: feat / fix / perf / refactor / chore / docs / ci / style / test
- `scope`: 바뀐 영역 (catalog, embed, deploy, obs, s3, db, vlm …). 애매하면 생략
- 한국어. 마침표 없음. 50~72자 안쪽
- 가능하면 **결과나 판단**을 담는다 — "X를 추가" 보다 "X를 Y로 전환", "A는 B가 아니다"

좋은 예 (레포 실제 커밋):

```
fix(catalog): PDF가 아닌 파일 제외 + 0청크를 경고로 드러냄
fix(s3): boto3에 region을 명시 — AWS_REGION은 boto3가 읽지 않는다
feat(deploy): 인덱싱을 호스트 cron에서 컨테이너 상시 데몬으로 전환
```

## 본문

순서: **문제(관찰) → 원인 → 조치 → 검증**

- **`##` 마크다운 헤더를 쓰지 않는다.** 평문 단락과 목록만 쓴다
- 문제부터 시작한다. 가능하면 운영에서 관찰한 구체적 수치로 (`5027건을 모두 처리했으나 전부 0청크였다`)
- 원인은 기전을 짚는다 — 파일명·함수명·환경변수명을 그대로 적는다
- 원인이 둘 이상이면 `1)` `2)` 로 번호를 매긴다
- 변경 항목 나열은 `- ` 불릿. 파일별로 묶어도 좋다
- 한 줄 100자 안쪽에서 접는다
- 평서형 `-다` 체. 사과·수식어 없이 사실만

### 검증

**본문 마지막은 `검증:` 으로 끝낸다.** 이 레포의 관습이다.

무엇을 어떻게 확인했는지 구체적으로 적는다. "테스트 통과"만 쓰지 않는다.

```
검증: 실제 로그에 나온 파일명 표본으로 필터 확인(.pdf/.PDF는 통과, .txt/.zip/확장자없음은
제외, 파일명 NULL은 판별 불가라 시도). 이미지 빌드 및 CLI 기동 확인.
```

확인하지 못한 것이 있으면 숨기지 말고 적는다 — `운영 Ollama 상대로는 미검증(테스트는 가짜 응답)`.

## 이슈 참조

- 이슈를 닫으면 `Closes #12`
- 관련만 있으면 `Refs #12`
- 본문 맨 끝, `검증:` 다음 줄

## PR 본문

커밋 본문과 같은 원칙이다. 다만 리뷰어를 위해 조금 더 풀어 쓴다.

- 제목은 커밋 제목과 같은 형식
- 첫 문단에 **왜 이게 필요한지** — 관찰된 문제부터
- 표는 비교(전/후, 항목별 판정)에만 쓴다. 설명을 표로 쪼개지 않는다
- `## 검증` 절에 실제로 돌린 것을 적는다
- 배포 시 주의할 점이 있으면 마지막에 `## 배포 시`
- **다른 레포·다른 팀의 시스템을 근거로 끌어오지 않는다.** 우리 사정만으로 설명한다

## 커밋을 나누는 기준

한 커밋 = 한 가지 판단. 되돌릴 때 그 판단만 되돌아가야 한다.

- 기능 변경과 대량 포맷팅을 섞지 않는다
- 리팩터링과 동작 변경을 섞지 않는다
- 다만 "고치다 보니 같이 드러난 것"은 함께 담고 본문에 그렇게 적는다
