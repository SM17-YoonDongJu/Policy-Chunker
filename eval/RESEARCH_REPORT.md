> 2026-08-10. 보험약관 PDF 청킹 개선을 위해 조사한 외부 자료 7건의 핵심 정리.

## 한눈에 보기

| 자료 | 한 줄 핵심 | 우리에게 주는 것 |
|---|---|---|
| InsQABench (arXiv 2501.10943) | 보험약관은 범용 파서로 안 되고, 보험사별 규칙 기반 문단 재조립 + 노이즈 제외가 필수 | 본문 길이 하한, 반복검색(ReAct) 아이디어 |
| PolicyBot (arXiv 2511.13489) | 조항 완결성을 지키는 청킹이 고정 크기 분할을 이긴다 | 우리 조 단위 청킹 방향의 타당성 근거 |
| RAG 실증평가 (arXiv 2601.15457) | cross-encoder 리랭킹이 가장 확실한 이득 (faithfulness 상대 +28%) | rerank 프로덕션 반영 근거 |
| Chunking 체계분석 (arXiv 2601.14123) | overlap은 무익, ~2.5k 토큰 넘으면 품질 절벽 | 청크 크기 상한 점검 기준 |
| OHRBench (arXiv 2412.02592) | 표 구조 오류가 파싱 오류 중 가장 치명적 (F1 -50%) | 표 품질 지표 추가 근거 |
| AutoRAG 한국어 실측 (velog) | 한국어에서도 semantic > recursive/token 실측 확인 | 한국어 도메인 참고 수치 |
| LoyJoy (실무 블로그) | 보험약관 RAG 실패 3원인: 상호참조·유사도≠관련성·구조 소실 | 실패 유형 분류 프레임 (단, 상호참조는 우리 데이터선 원인 아님) |

**교차 결론 (자료들이 수렴하는 지점):**
1. **구조 보존 청킹 > 크기 기반 분할** — 전 자료 일치. 조항/문단의 논리적 완결성이 검색 품질의 상한을 정한다.
2. **2단계 검색(retriever + cross-encoder rerank)은 선택이 아니라 필수** — 가장 확실하고 큰 이득.
3. **노이즈(목차·부록·회사정보)는 인덱스에서 빼는 게 정석** — 진지한 시스템은 전부 이렇게 함.
4. **표 구조 보존이 파싱의 최우선 리스크** — 표가 깨지면 하류에서 복구 불가.
5. **아무도 깔끔히 못 푼 것: 멀티스텝 추론** (여러 조를 조합해야 하는 질문) — 청킹만으로는 안 되고 반복검색/그래프 레이어가 필요.

## 1. InsQABench — 중국 보험약관 QA 벤치마크 (arXiv 2501.10943)

**뭘 했나**: 실제 중국 보험사 약관 PDF로 QA 벤치마크 3종(상식 QA / 구조화 DB QA / **약관 조문 QA 40k**)을 구축. 약관 조문 QA의 전처리 파이프라인이 우리와 직접 겹침.

**핵심 방법**:
- **파싱**: Adobe PDF Extract API로 element+바운딩박스 추출 → **보험사별 조문 레이아웃에 맞춘 커스텀 규칙**으로 bbox 기반 문단 재조립. "회사마다 레이아웃이 달라 규칙 기반 후처리가 필수"가 결론. (단, 구체 임계값·좌표 조건은 논문에 없음)
- **청킹**: 문단 단위. **최소 50자(한자) 미만은 정보 부족으로 폐기.**
- **노이즈 제외**: 문서 앞의 목차·회사정보, 문서 끝의 부록을 **의도적으로 인덱스에서 제외.**
- **검색(RAG-ReAct)**: BGE-M3 + Faiss에 LLM이 반복 질의 — 1차 검색 → LLM이 쿼리를 다듬어 재검색 → `<AnswerReady>` 신호까지 반복. 이 루프로 fine-tuned GLM4(83.63)가 GPT-4(76.23)를 역전.
- 약관 표 처리는 사실상 서술 없음 (표는 별도 구조화 DB 트랙).

**시사점**: ① 도메인 규칙 기반 재조립은 정석 (우리도 이미 함) ② 본문 정보밀도 하한은 우리가 놓친 부분 ③ 반복검색은 랭그래프 레이어에서 도입 가치.

## 2. PolicyBot — 정책문서 QA (arXiv 2511.13489)

**뭘 했나**: 정책문서 QA 챗봇. **청킹 전략 비교 실험을 직접 수행**한 드문 사례.

**핵심 방법·결과**:
- **시맨틱 청킹** (LangChain semantic splitter, breakpoint=standard_deviation, threshold=1.0) vs **recursive** (750~1000자, overlap 200~250자) 비교 → **낮은 k에서 시맨틱이 일관되게 우세.** 이유: "임의 지점 분할은 법률 조항의 의미를 왜곡하거나 필수 문맥을 누락시킨다" — 조항 완결성 보존이 핵심. (정확한 수치는 그래프로만 제시, ablation 없음)
- **검색 스택**: HyDE(가상 답변 생성) + 멀티쿼리 + RRF + cross-encoder 리랭킹. 우리 스택(RRF + bge-reranker + 리라이팅)과 거의 동일 구성.
- **전처리 결정**: 페이지 1장=문서 1건, 헤더/푸터 제거 안 함(파괴 위험 회피), 메타데이터는 페이지번호+파일명만.
- 답변 아래 근거 청크를 접이식으로 노출 → 사용자 검증 가능.

**시사점**: "조항의 논리적 완결성을 유지한 청킹이 검색 품질을 좌우"가 실험으로 확인됨 — 우리 조 단위 청킹 방향의 외부 근거. HyDE는 우리가 아직 안 해본 기법.

## 3. Chunking, Retrieval, Re-ranking 실증평가 (arXiv 2601.15457)

**뭘 했나**: 정책문서 QA에서 RAG 구성요소별 기여도를 정량 측정.

**핵심 수치**:

| 지표 | Vanilla LLM | Basic RAG | Advanced RAG (+cross-encoder) |
|---|---|---|---|
| Faithfulness | 0.347 | 0.621 (+79%) | 0.797 (상대 +28%) |
| Relevance | 0.450 | 0.700 | 0.800 |

- cross-encoder 관련성 85~90% vs bi-encoder 65~80%.
- **멀티스텝 추론 병목**: bi-encoder는 질의-문서 joint attention이 없어 인과관계를 놓침 → 여러 조를 조합해야 하는 질문에서 초기 벡터검색이 관련 조를 후보에 못 올림. 사례: 벡터검색이 무관한 문맥을 가져와 0.00점 → cross-encoder 도입으로 0.80 회복.
- "document segmentation의 구조적 제약이 multi-step reasoning의 병목"이라 결론.

**시사점**: 리랭킹은 가장 확실한 투자. 우리 실측(rerank R@1 +10.6pp)과 방향 일치. 멀티스텝은 청킹이 아니라 검색 루프에서 풀어야 함.

## 4. A Systematic Analysis of Chunking Strategies (arXiv 2601.14123)

**뭘 했나**: 4개 청킹 방식(token/sentence/semantic/code)을 SPLADE retriever + Mistral-8B로 체계 비교 (Natural Questions).

**핵심 결과**:
- **overlap: 측정 가능한 이득 없음.** 인덱싱 비용만 증가 → 쓰지 마라.
- sentence 청킹이 가장 비용효율적 — **~5k 토큰까지 semantic과 동등.**
- **~2.5k 토큰 초과 시 "context cliff"** — 품질 급락. semantic 품질은 작은 컨텍스트에서 정점.

**시사점**: 우리 target=500/hard_max=1000 토큰 설정은 안전권. overlap 미사용도 정당화됨. 큰 blob 청크(제5조 700토큰)가 왜 불리한지의 이론적 근거.

## 5. OCR Hinders RAG / OHRBench (arXiv 2412.02592)

**뭘 했나**: 파싱/OCR 오류가 하류 RAG 성능에 미치는 연쇄 영향을 정량화. 350 PDF·4,012페이지, 전문가 교정 ground truth, 오류를 3단계(mild ~10% / moderate ~30% / severe ~50%)로 주입.

**핵심 결과 — 오류 2분류**:

| 유형 | 정의 | 하류 영향 |
|---|---|---|
| **Semantic Noise** | 오타, 수식 오인식, **표의 셀/구조 오류(행·열 붕괴)** | **치명적** — 대부분 retriever·LLM에서 ~50% 하락. 표 질문에서 GPT-4o F1 **-50%** |
| **Formatting Noise** | 공백·bold·마커, 표 표현 차이(MD vs LaTeX) | 경미 — plain-text 질문 거의 무영향 |

- **Edit distance ≠ 하류 성능**: 파싱 지표가 좋아도 RAG 성능이 따라오지 않는 경우 존재 → **파싱 품질은 end-to-end(retrieval+generation)로 재야 한다.**
- 최고 OCR도 ground truth 대비 ≥7.5% 갭.

**시사점**: 표 구조 보존이 파싱의 1번 리스크. 우리 coverage 지표는 파이프·공백을 정규화로 지워버려 **표가 깨져도 못 잡는 맹점**이 있음 → 표 구조 충실도 지표 필요.

## 6. AutoRAG — 한국어 청킹 실측 (velog)

**뭘 했나**: 한국어 문서 40문항으로 청킹 방식별 답변 품질 실측 (semantic은 OpenAI 임베딩).

**핵심 수치**:
- G-Eval Consistency(1~5): No Chunk 3.077 < Token 3.231 < Recursive 3.308 < Window 3.359 < **Semantic 3.513**
- 정성평가(17문항, 환각 -1점): No Chunk 0.353 < Recursive 0.471 < Window 0.588 < Token 0.647 < **Semantic 0.794**
- 단, semantic은 코퍼스 구축 9분 vs 타 방식 3~10초.

**시사점**: 한국어에서도 의미 경계 기반 분할이 우세. 우리 "조 단위 = 도메인 지식으로 의미 경계를 공짜로 얻는 방식"이므로 semantic의 상위 호환일 가능성 — 직접 비교 실험은 아직 안 함.

## 7. LoyJoy — 왜 AI가 보험약관에서 실패하는가 (실무 블로그)

**핵심 주장 — 일반 RAG의 실패 3원인**:
1. **상호참조**: 5조의 보장은 12조의 면책과 함께 읽어야 유효한데 청크는 이를 모름.
2. **유사도 ≠ 관련성**: 결정적인 면책조항은 질문과 안 비슷하게 들림.
3. **구조 소실**: 같은 문장도 "보장" 섹션이냐 "계약자 의무" 섹션이냐에 따라 법적 의미가 다른데 청킹이 버림.

해법으로 사전 청킹 대신 에이전트가 문서 구조를 직접 읽는 agentic retrieval 채택.

**시사점 (우리 데이터로 검증한 결과)**: 우리 exclusion 실패 7건을 역추적한 결과 **상호참조(①)는 원인 0건** — 한국 약관의 면책조는 자기완결적 리스트라서. 반면 **②유사도≠관련성은 실재** (전쟁·폭동 문구가 24개 특약에 중복돼 변별 불가). 즉 이 프레임은 유용하지만 도메인 데이터로 검증 후 취사선택해야 함.
