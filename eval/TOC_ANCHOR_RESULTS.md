# 목차 앵커 + 리셋 기반 분할 — 설계와 실측

> 2026-08-11 / 코드: `insurance_chunker/toc.py`(신설), `rechunk.clean()` 리셋 분할
> 측정: `eval/toc_score.py` (보험사 6곳, 이어받기 지원)

---

## 1. 왜 만들었나 — 기존 지표가 우리를 속이고 있었다

전날 KB 문서에서 경계 검출이 붕괴한 걸 발견했는데(섹션 7개), 정작 **기존 지표는 그걸
말해주지 못했다.** 오히려 반대로 말했다.

| 지표 | 붕괴 시 나오는 값 | 왜 |
|---|---|---|
| `gaps`(조 결번) | **0** (최고점) | 여러 특약이 한 섹션으로 뭉치면 1~N조가 다 들어차 결번이 생길 수 없다 |
| `art_nonmono` | **0** (최고점) | 특약을 아예 못 잡으면 조번호 리셋 자체가 관측되지 않는다 |

실제로 DB프로미라이프는 `nonmono=0`으로 6곳 중 1등이었는데, 목차 대조로 보니
**132개 중 84개를 놓치고 있었다**(점수 0.280, 5위). 대리지표의 한계다.

**우리가 정말 알고 싶은 것은 "약관이 선언한 특약을 우리가 찾았는가"** 인데,
그걸 재려면 정답이 필요하고 정답을 사람이 만들면 보험사 수만큼 비용이 든다.

→ **목차를 쓰면 된다.** 목차는 조판이 아니라 **문서가 스스로 선언한 데이터**다.

## 2. 무엇을 만들었나

### 2-1. `insurance_chunker/toc.py` — 목차 수확기

보험사마다 목차 조판이 달라서 4가지를 모두 지원한다(6개 문서 실측으로 확인):

| 형식 | 예 | 해당 |
|---|---|---|
| A. 점선 리더 + 페이지번호 | `…특별약관······ 123` | 메리츠, DB프로미 |
| B. 점선만, 번호 없음 | `약관 이용 가이드북······` | KB |
| C. 제목과 번호가 다른 줄 | `보통약관` / `62` | 삼성 |
| D. 번호 없이 들여쓴 제목 | `  외상성절단진단비 특별약관` | DB빅히트 |

기존 `boundary_eval.reference_from_toc()`는 A만 지원해 **3/6에서 0건**이었다.
부가 처리: 감긴 제목 잇기(`…(감액없` + `음)`), 전화번호·URL·안내문 제외,
`is_title_like()` 통과 필터, `front_end`가 비정상적으로 작을 때 스캔 범위 보정.

### 2-2. 자가검증 점수 (`eval/toc_score.py`)

```
점수 = 목차가 선언한 특약 중 검출 섹션으로 커버된 비율
```
조판 줄바꿈·번호 표기 차이 때문에 완전일치가 아니라 **양방향 부분일치**로 대조한다.
골든셋이 없어도, 보험사가 몇 곳이든 **문서가 스스로 채점한다.**

### 2-3. 리셋 기반 분할 (`rechunk.clean()`)

핵심은 **경계의 "위치"와 "이름"을 분리**한 것:

```
조번호 리셋(N→1)  →  경계 위치   (폰트·접미사와 무관한 구조 신호)
목차 제목 목록     →  경계 이름   (문서가 선언한 데이터)
```

리셋을 만나면 이름을 3단계로 찾는다:
1. 인라인 제목 (직전 조각 끝의 제목 줄 — 기존 v6 로직)
2. **목차 순서 매칭** — 리셋 주변 800자에서 아직 안 쓴 목차 제목을 찾음
3. **합성 라벨** (`{상위라벨} · 구분N`) — 이름을 못 찾아도 **분할은 한다**

3번이 설계의 핵심이다. **이름이 틀린 것보다 내용이 섞이는 게 검색에 더 해롭다.**
`RECHUNK_RESET_SPLIT=0`으로 이전(v6) 동작 복귀 가능.

## 4. 드러난 다음 병목

### 4-1. 현대해상 — 목차 복합항목 (`A특별약관/B특별약관`)

경계를 124개 더 만들었는데 점수가 **정확히 0.000** 올랐다. 목차 항목이 이렇게 생겼다:

```
1-13상해입원일당(1-10일)보장특별약관/상해입원일당(1-10일)[맞춤고지Ⅰ]보장특별약관
```

**한 줄에 두 특약이 `/`로 묶여 있다.** 정규화하면 두 이름이 붙은 문자열이 되는데
본문엔 각각 따로 나오므로 매칭이 안 된다. → 목차 항목을 `/`로 분할해야 한다.
실제 목차 항목 수도 267 → 400+ 로 늘 것이다.

### 4-2. DB프로미라이프 — 리셋 신호 부재

`nonmono=0`이라 리셋 기반 분할이 발동조차 안 한다. 놓친 84개 특약의 본문이
어디로 갔는지(조번호가 안 붙었는지, 다른 섹션에 흡수됐는지) 별도 조사가 필요하다.
`table_page_recall`도 6곳 중 유일하게 0.9 미만(0.844)이라 연관 가능성 있음.

### 4-3. KB — 0.440에서 멈춘 이유

목차 904개 중 아직 507개 미매칭. 리셋이 일어나지 않는 구간(특약이 1~2조로 짧아
리셋 판정 조건 `cur_art >= 2`에 안 걸리는 경우)이 원인일 가능성이 크다.

## 8. 2차 개선 — 목차 복합항목 분할 + 짧은 특약 리셋 (8/11)

§4의 병목 3건 중 2건을 처리했다.

### 8-1. 목차 복합항목 분할 (`toc._split_compound`)

현대해상 목차는 한 줄에 두 특약을 `/`로 묶는다. 괄호 안의 `/`는 한 이름의
일부이므로(`(3.5.5간편고지/3.2.5간편고지)`, `(비갱신형/갱신형)`) **괄호 깊이를
추적해 depth 0인 `/`에서만** 자른다.

효과가 예상보다 컸다 — 목차 항목 **267 → 898개**. 두 가지가 동시에 풀렸기 때문:
1. 두 특약이 묶인 항목을 각각 매칭 가능하게 만들었고,
2. **합쳐진 문자열이 80자를 넘어 통째로 버려지던 항목**을 되살렸다(쪼개니 각
   조각이 길이·형식 필터를 통과).

### 8-2. 짧은 특약 리셋 인정 (`n_since_art`)

기존 리셋 조건은 `직전 조 ≥ 2`라서 1조짜리 특약이 연달아 오면 `1→1`이 되어
리셋으로 안 쳤다. 직전 제1조가 실제 본문을 가졌을 때만(`n_since_art >= 1`)
추가로 인정하도록 완화 — 같은 조 헤딩이 두 번 매치되는 오탐은 이 조건이 막는다.

**결과: 가설 빗나감.** KB 검출 297 → 301(+4), 점수 0.440 → 0.440으로 무변화.
짧은 특약의 리셋 누락은 KB 정체의 주요 원인이 아니었다.

## 9. 남은 과제 (갱신)

1. **KB 0.44 정체의 진짜 원인** — 목차 904 vs 리셋 기반 경계 ~300.
   600여 개가 리셋 신호를 안 만든다. 유력 가설: 목차의 `245-1. …【갱신계약】`류
   **갱신계약 변형 항목이 본문에선 별도 특약 구간이 아닐 가능성** — 그렇다면
   분모가 부풀려진 것이고 달성 가능한 상한 자체가 0.44 근처다. 미매칭 항목의
   성격을 직접 확인해야 판단할 수 있다.
2. **DB프로미라이프 0.280** — 리셋 신호도 없고(`nonmono=0`) 목차 복합항목도 없어
   두 수정 모두 해당 없음. 놓친 84개 특약의 본문 행방을 조사해야 한다.
   `table_page_recall` 0.844(6곳 중 유일하게 0.9 미만)와의 연관 가능성.
3. **삼성 0.484** — 목차 521개 그대로. 복합항목이 아닌 다른 원인.
