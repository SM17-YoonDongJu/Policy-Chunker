# Policy-Chunker 개선 로그 (전체 히스토리)

> 한국 보험약관 PDF를 RAG용 청크로 변환하는 파이프라인의 전체 개선 기록.
> 기간: **2026-06-02 ~ 2026-08-10** (78 커밋). 여러 Claude 세션(Fable 5 / Sonnet 5 / Opus 4.8)에 걸쳐 진행.
>
> 각 항목은 **문제 → 원인 → 조치 → 실측 근거** 순으로 적었고, 수치는 커밋 메시지·평가 결과 파일에 기록된 실제 측정치를 인용한다.
> 관련 문서: [`RESEARCH_REPORT.md`](RESEARCH_REPORT.md)(외부자료 조사), [`GAP_ANALYSIS.md`](GAP_ANALYSIS.md)(코드 대조·백로그), [`WORK_LOG_3DAYS.md`](WORK_LOG_3DAYS.md)(8/8~10 상세), [`RETRIEVAL_EVAL_CONTEXT.md`](RETRIEVAL_EVAL_CONTEXT.md)(평가 인수인계).

## 0. 큰 그림 — 파이프라인이 어떻게 진화했나

```
PDF ──▶ 파싱 ──▶ 경계 검출 ──▶ 재청킹(조 단위) ──▶ 분류 ──▶ 임베딩 ──▶ 저장 ──▶ 검색
       pdf_parser  boundaries    rechunk          llm_classifier embedder  storage   db/search
                                 + chunker                                  (+S3 표)
```

프로젝트는 3개의 큰 국면을 거쳤다:

| 국면 | 기간 | 한 줄 요약 |
|---|---|---|
| **A. 기반 구축** | 6/2 ~ 6/20 | Policy-Chunker(폰트 기반 경계) + rag 파이프라인(메타/임베딩/스토리지) 통합, DB 스키마 확정 |
| **B. 품질·검색 도입** | 7/30 ~ 8/4 | LLM 분류기·VLM 백엔드·평가 스위트 구축, 리랭커+쿼리 리라이팅으로 검색 도약, RAG 계약 API |

## 국면 A — 기반 구축 (6/2 ~ 6/20)

### A-1. 초기 설계: 하드코딩 제거, 폰트 신호 기반 자동 탐지 (6/2)
- **배경**: 원본 Policy-Chunker는 문서마다 제목 폰트 크기(12.9)·보통약관 시작 페이지(p16) 등을 하드코딩했다. 이걸 문서 신호에서 자동 추론하도록 전환.
- **구성**: `boundaries.py`(제목 폰트·보통약관 시작·상품명 자동 탐지), `rechunk.py`(약관 라벨 + 조번호 재추출 + 푸터/목차 제거 + 호→항→조 병합 + 헤더 prepend + 중복 제거), `combine.py`(표 best-of: 더블스페이스 적은 소스 채택).
- **근거**: 레퍼런스 문서에서 자동 탐지가 옛 하드코딩값을 재현 — 제목폰트 12.9, 보통약관 p16, 약관 138개/별표 17개, 제47조 누수 0.
- **저작권 설계**: `.gitignore`가 약관 원문·청크·파생물을 전부 제외 — 코드만 커밋하는 원칙(지금까지 유지).

### A-2. 표 추출 4소스 + VLM + 신뢰도 게이트 (6/2)
- `extract.py`: PyMuPDF 본문/표 + pdfplumber + camelot + VLM(claude CLI). 여러 소스로 표를 뽑아 `combine`이 best-of 선택.
- `boundaries.assess()` **신뢰도 게이트** 도입: 조문 구조가 약한 약관(표 중심·스캔본)은 🔴로 걸러내 잘못된 청킹을 애초에 막음.

### A-3. rag 파이프라인 통합 (6/2 ~ 6/3)
- Policy-Chunker의 경계·표 로직을 베이스로, rag/ 파이프라인의 메타데이터·임베딩·스토리지를 통합해 `insurance_chunker` 패키지로 재구성.
- `embedder.py`(Ollama / BGE-M3 듀얼 백엔드), `chunker.py`(doc_type별 오케스트레이터), `tokenizer.py`(kiwipiepy를 subprocess로 격리 — C레벨 크래시가 파이프라인 전체를 죽이는 것 방지).
- 의존성 정리: anthropic·tiktoken·paddleocr 제거. tiktoken 토큰 카운트 → 글자 수 근사로 대체.
- **요약서(product_summary) 제외**: 상품 요약서는 청킹·저장·임베딩 모두 스킵.

### A-4. DB 스키마 확정 & "yakwan 컬럼" 6일 전쟁 (6/6 ~ 6/7)
이 기간은 데이터 모델을 확정하는 과정에서 **한 필드(yakwan=특약명)를 넣었다 뺐다를 8커밋에 걸쳐 반복**한, 설계 수렴의 기록이다.

- 흐름: `yakwan` 추가 → "section이 이미 특약명을 담으므로 중복" 판단으로 제거 → `report()`가 참조해서 크래시 → 내부 필드로 복원 → 다시 완전 제거 → 잔재 청소 → `report()` 통계는 bounds에서 직접 집계하도록 재구현.
- **교훈이 남은 결정**: "출력 컬럼 = DB 컬럼" 원칙 확립. 최종적으로 `insurance_chunks` → **`policy_chunks`** 테이블로 재설계(18개 컬럼), `parent_id`/`structured_json`/`section_path` 같은 항상-None인 dead field 전면 제거.

### A-5. 검색 인덱스 방식의 변천 (6/6 ~ 8/14)
키워드 검색 백엔드를 세 번 바꿨다:
1. tsvector + trigram (6/6)
2. → **pg_search BM25** (6/7, `content_tokens @@@` + paradedb.score)
3. → 다시 **tsvector GIN** (8/14) — 최종. `search_terms` 테이블(형태소 사전, trigram 오타교정용)은 별도 유지, `rebuild_search_terms.py`로 분리(advisory lock으로 멀티머신 안전).

### A-6. 큰 표의 S3 분리 저장 (6/7)
- 20행 초과 표는 `TableMeta`(부모, markdown 전문)로 만들고 20행씩 자식 청크로 분할, 헤더 행을 매 청크에 재삽입.
- 표 원본 markdown은 **Postgres가 아니라 S3**에 저장(`policy-tables/{table_id}.md`), `table_id`는 plain S3 키. S3 미설정 시 `.table_cache/` 로컬 폴백.
- `chunk_index` 도입: 표 자식 포함 문서 전체 순서 — 검색 후 조항 원문 복원용 정렬 키.

### A-7. 저장 효율화 (6/20)
- 임베딩을 `vector(1024)` → **`halfvec(1024)`**(float16)로 전환. 수백 종 약관 적재 시 임베딩·HNSW 인덱스 용량과 RAM을 절반으로. 1024d에서 정확도 손실은 무시 가능.

### 4-A. 운영·실행 트러블슈팅

   **세션과 완전히 분리한 프로세스**로 띄워서야 살아남았고, 이후 모든 장시간 작업(17문서 배치, Surya 추론, v6 평가)을
   같은 방식으로 실행. → 원칙: **장시간 작업은 세션 독립 프로세스 + 이어받기 가능하게.** (6월 "다운로드 6회 끊김 → resume 원칙"과 같은 계열)
2. **조사 스크립트 타임아웃 — PDF 재파싱의 비용.** nonmono 원인 조사용 재청킹 스크립트가 2분→6분 타임아웃으로

### 4-B. 청킹 방법론 — 왜 그렇게 결정했나

4. **호 분할을 "면책 한정"이 아니라 "일반 규칙"으로 시작한 이유.** 면책만 좁히면 다른 나열형 조문의 같은 문제를
   영영 못 보게 되므로, 일반 규칙(토큰 ≥400 && 항목 ≥4)으로 한 번 재보고 데이터가 부작용을 보이면 env 노브로
   좁히는 전략. 결과적으로 게이트를 통과해 좁힐 필요가 없었다.
5. **v5 과분할 우려 — 실행 전에 시나리오·폴백을 먼저 세움.** 1250청크(2.7배)·특약 조 최대 24조각에 대해
   ① 후보풀 잠식(rerank top20을 형제 조각이 도배) ② 저정보 조각 양산(InsQABench가 경고한 문제로의 회귀) 리스크를
   명시하고, 낙관 60%/비관 40% 시나리오와 폴백(임계값 상향 or 면책 한정 축소)을 미리 적은 뒤 eval에 판정을 맡겼다.
6. **경계 복구를 소폭 개선에서 멈춘 이유.** 잔존 nonmono는 다른 실패 유형(여러 줄 제목·제2조 시작)이라 규칙을
   공격적으로 만들면 잡히지만 **"문장 조각이 특약 라벨로 오승격"되는 위험**이 커진다. 회귀 없는 소폭 개선에서 멈추고
   검색 지표(v6 전 지표 상승)로 판정받는 쪽을 택했다.

### 4-C. 평가·데이터 함정 (빠질 뻔한 것들)

7. **v5 boilerplate 필터링 함정.** `make_chunks_jsonl`은 boilerplate 포함 1837청크를 출력하는데 v3 파일은 이미
   587개가 제거된 464청크 — 모르고 비교했으면 v5가 불공정 측정될 뻔. 587개 필터 후 1250청크로 맞춰 공정 비교.
   → 버전 비교 전 "두 파일이 같은 후처리를 거쳤는가" 확인.
8. **coverage 측정 아티팩트.** 호 분할 후 coverage가 5~8%p 낮게 측정(실유실 아님) — 검사 프로브(연속 12자)가
   분할 경계를 가로질러 false-missing. `batch_integrity.py` 주석에 "같은 코드 버전끼리만 비교" 명시.
9. **"VLM 승률 67.3%"와 "ragged 무개선"은 모순이 아니다.** 승률은 정렬·공백 품질(더블스페이스), ragged는 구조
   붕괴(행별 열 개수) — 재는 게 다르다. VLM은 전자를 개선하지만 후자의 원인(병합셀→markdown 평탄화 손실)은
   표현 형식의 문제라 추출기로 못 고침. → 지표가 좋아 보여도 "정확히 뭘 재는지"를 따져야 투자 판단이 안 틀린다.

### 4-D. 미해결·배포 주의사항

10. **재인덱싱 체크리스트.** 질의 프리픽스(버그 A)는 질의 벡터에만 영향 → 재인덱싱 불필요. 임베딩 태그(버그 B)는
    기존 운영 DB의 색인 모델에 따라 재인덱싱 필요 여부가 갈림 — 이 세션에선 운영 DB 확인 불가라 "배포 전 확인"으로
    남김. v6 청킹 반영 시엔 재청킹+재인덱싱 + **`SEARCH_RERANK=1` 필수**(v6은 rerank 전제로만 v3를 이김).
11. **랭그래프 레이어 배치.** 청킹 레이어(이 레포, 오프라인) / 검색 함수 레이어(`db/search.py`, rerank 켜기만) /
    그래프 레이어(rewrite 노드, 반복 ReAct 검색 — conditional edge로 CRAG 패턴, 최대 1~2턴 캡, Q12 총칙 부스트)로
    수정을 3층 분리. 핵심 판단: **반복검색은 단발 API에선 리스크였지만 랭그래프에선 프레임워크가 그 리스크
    (루프 제어·정지 조건·상태 관리)를 해결해준다.**
12. **claude 청킹과의 남은 격차 = 정확히 Q12 하나.** "전쟁·폭동" 문구가 24개 특약에 verbatim 복제돼 검색으로
    변별 불가(claude도 못 맞춤). 청킹·리라이팅으론 불가, "면책 질의면 보통약관 총칙 우선" 메타데이터 부스트
    (그래프 레이어)만이 답. 골드라벨 협소성 판정도 부기.

### 4-E. 조사·분석 방법론 (재사용 가능한 프레임)

13. **exclusion 실패 원인 4분류 프레임.** (a) 검색 어휘 격차 / (b) 상호참조 문맥 부족 / (c) 청킹 오염·입도 /
    (d) 골드라벨 오류로 7문항 전수 분류 → 분포 (c) 2건, (a) 1건, (b) 0건, (d) 0건. 분포가 나온 순간 해법이
    "리라이팅 강화"가 아니라 "rechunk 수정"으로 확정. **원인 분포를 먼저 재면 해법 우선순위가 데이터에서 나온다.**
14. **교차검증 3종 — 단일 증거로 결론 내지 않기.** "호 단위 세분할이 claude 우위의 원인" 가설을 ① 유형별 분해
    (우위가 BM25·rerank에 집중, embed는 동률 → term-density 메커니즘) ② 기존 실험 재활용(`small2big.log`의
    exclusion 0.71 — 독립 증거) ③ 반례 확인(v4/v4b는 blob 유지 → exclusion 하락)로 3중 검증.
15. **small2big 재해석 — "평균"이 숨긴 유형별 신호.** 8/4에 전체 평균 동률로 보류했던 실험이, 8/10에 exclusion
    유형만 분해하니 0.43→0.71 급등으로 재발견 → "전면 도입이 아니라 나열조만 선택 분할"이라는 v5 설계의 근거.
    → **실험을 기각할 때도 유형별 분해를 남겨둘 것. 평균으로 버린 것이 부분집합에선 답일 수 있다.**
16. **계획 방식.** 8/10 조사는 [분석 1~4 병렬(서브에이전트)] → [갭 분석 통합] → [백로그+사용자 확인] →
    [구현+eval 검증]의 의존성 그래프로 실행. 각 분석의 출력 계약을 "그들이 한 것 → 우리 코드(파일:함수) → 갭"
    대조표로 통일해 통합 비용을 낮췄다.
